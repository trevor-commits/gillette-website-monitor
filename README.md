# Gillette website monitoring

Owner: Trevor Gillette. Purpose: independent public HTTPS/readiness checks and daily non-submitting browser/dependency checks for https://gillettewsc.com. Integration target: main. Operational exit condition: verified scheduled executions and independent DOWN/UP delivery, with current recovery instructions.

Standard ubuntu-latest runners in this PUBLIC repository avoid private-repository Actions minutes. No paid runner, matrix, automatic retries or deployment. The HTTP/browser checks use no customer data. HTTP checks run every fifteen minutes; browser checks daily at18:00UTC. GitHub schedules can be delayed. Independent Healthchecks deadlines detect missing runs: HTTP15minutes plus20minutes grace; browser24hours plus4hours grace. Fixed failure/success signals go to Trevor through an existing Email integration, independently of the website Worker/D1/Resend/Mac. Secret ping capabilities are stored only in Actions secrets.

The HTTP probe resolves public DNS and validates public HTTPS by normal Node fetch, checks homepage content and full readiness. The browser probe checks live form JavaScript, Google address suggestions, initialized Turnstile and analytics transport; it blocks all lead POSTs and uses only labeled synthetic/public input. No CAPTCHA solving, customer record or quote email. Headless Umami bot filtering is explicitly transport-only; owner dashboard inspection still proves actual event ingestion.

Manual activation can use forceFailure=true for one isolated observer failure, then a normal run for recovery. It changes only the observer signal and never production. runBrowser=true dispatches the daily browser job for verification. No pull-request workflow or untrusted code receives secrets.

## Encrypted backup preparation

The separate `backup.yml` is prepared for six-hour runs at00:40/06:40/12:40/18:40UTC, with one ten-minute Ubuntu job and no push/pull-request triggers. It is inactive unless repository variable `GILLETTE_BACKUP_ENABLED` is exactly `true`; a skipped job is not backup proof. Activation and credential transfer require the business owner's applicable approval. The existing Mac backup remains until an actual hosted calendar run, independent download/decryption, isolated application restore and bounded warning/recovery test are verified.

`backup-leads.mjs` is the identical operational artifact from the website's `scripts/backup-leads.mjs`; maintain it at that source, run its focused regression tests there, and compare SHA256 before publication. The hosted path uses a dedicated Cloudflare D1 Read token; it must not receive the Mac's broader Wrangler OAuth credential. Export API status is polled promptly, at most20times within three minutes. Signed downloads are HTTPS Cloudflare R2 only, limited to64MiB, and never receive the Cloudflare bearer token.

The runner temporarily processes private inquiry SQL, checks an isolated in-memory SQLite restore, encrypts with the existing AES256GCM recovery key, then uploads only ciphertext into the existing private business Drive folder. It independently downloads, hashes and decrypts that copy before reporting success. The existing dedicated drive.file connection can manage only files created by that connection. No private website checkout, plaintext/key/credential artifact, customer content in logs or production restore is allowed. This workflow has no notification-sending or database-write credentials. Actions secrets hold its read token, dedicated Drive configuration, recovery key and independent warning capability. Repository variables identify the intended account, database and Drive folder. Runner-private files are mode0600 under its unique temporary directory and removed even on failure.

Keep30days of exact timestamped snapshots. Older copies go to recoverable Drive Trash only after a verified replacement. The last verified Drive copy survives a failed run. A six-hour Healthchecks period plus two-hour grace warns independently after eight hours without a good backup; this protects the24-hour recovery-point target. Restores require the separately retained recovery key and an operator-controlled isolated application check; the recovery-time target is four hours. Run `forceFailure=true` only for one approved Trevor-only warning test, then dispatch a normal run and verify recovery. Missing-run warning remains required because GitHub schedules can be delayed or disabled after inactivity.
